# P&ID QC with a markup PDF (RAW against OUTPUT)

This is the office's own working prompt for P&ID checking (from the QC lead), turned into a procedure and corrected with what the QC team met on real jobs. It goes further than `qc-pid` (which compares text): here the whole drawing is checked, graphics included, and the result is a **markup PDF on the OUTPUT**. Also read `qc-engineer-mindset` and `qc-findings-and-reports`.

## 0. Start
1. **Pair the files first, then read anything.** The two files must be the same drawing. File names usually show it (the same drawing number, ours with a suffix such as `-Model`: confirm on the title block). Read the **title block of both** (drawing number, unit, revision) and compare the tag scheme. `pid_compare` also reports `pair`: when its `warning` is set (few tags in common, or no text on one side) **tell the user first**, before you list any finding.
2. **Overview before text.** `pdf_render` the whole page of both (dpi about 40-60) and look. On a hand-marked RAW, **red = the new value, struck-through or blue-hatched text = deleted**; the redraw normally **incorporates** the red markups, so `pid_compare` reports many "FAILs" that are the markups themselves. Treat the text comparison as a hint, never as the finding. Whether the redraw is meant to carry the markups is usually clear from the sheets (its values equal the red ones); ask only when it is not.
3. **Identify RAW and OUTPUT yourself.** RAW = the client or vendor file: hand markups (red text, cyan highlights, green "NOTE FOR CADDING" boxes, struck-through text), often a scan or a plain PDF export. OUTPUT = our AutoCAD redraw: clean, standard symbols, our title block. Say which is which and why. If you cannot tell, ask.
4. **Drawing number from the title block** (read it on the drawing, not from the file name). The result file is named `<drawing number>_QC-Markup.pdf`, next to the OUTPUT, unless the user names a folder. The OUTPUT file itself is never changed.
5. **Plan the work and say it**: pages, zones, what you will check. If the session may stop (usage limit), keep the markup file saved after each sheet and say which sheets are done and which are left, so the work can be resumed with the next sheet.

## 1. Look at the drawing, by the sheet's own zones (never random cuts)
Drafting practice: a sheet is checked by the **grid zones of its border** (columns numbered along the top and bottom, rows lettered along the sides; a point is "zone J-12"), the same zones on the client's drawing and on ours. Do not cut a sheet into arbitrary pieces.
1. **`pdf_zones` on RAW and on OUTPUT** (page by page; give `cols` / `rows` with the labels you read on the border, for example `17-1` and `K-A`). It reads the real page size (A0 to A4, either orientation), finds the sheet's own grid from the border tick marks (the ISO 5457 grid of that size if there are none, and it says so: then read the border yourself), and gives review tiles that follow the grid with the zoom that suits the sheet (a scan is never rendered above its own resolution). **Give `across` / `down` the same on both drawings of a pair**, even when the sizes differ (an A3 scan against an A0 redraw): tile T2.2 of RAW is then the same part of the drawing as tile T2.2 of OUTPUT.
2. **`pdf_render` every tile** (`rect` and `dpi` from the plan) for RAW and for OUTPUT, open both pictures with the Read tool and compare them side by side. Look into a tile more closely (a smaller `rect`, higher dpi) when something is dense. A graphic you did not look at is not checked: say so at the end.
3. Text: if a side has a text layer, `pid_compare` / `pid_read` / `pdf_find` give the text with positions: use them as the first list of text differences, then confirm each on the picture. If a side has **no text layer** (a scan, or text drawn as lines: `pdf_zones` says `textLayer: false`), nothing is text-compared: read it from the pictures and say so. A long `pid_compare` answer lists the first problems and counts the rest per sheet (`problemsPerSheet`); ask for more with `maxProblems`, or read the saved file with the Read tool, never with a search.
4. **Read codes character by character** on the pictures: the class code in a line number (`A151` against `A15A`), a size (`1-1/2"` against `1/2"`), a tag suffix (`P-101A` against `P-101B`). They look right at overview zoom and are wrong at 200 dpi.
5. **Finding where to mark.** `pdf_find` gives the box of a text (whole words; several labels at once, `"PSV-512F|PSV-512G"`; `contains: true` for part of a word); use it first for short labels. For anything else (a symbol, an arrow, a line, text on a sheet without a text layer) measure the item **on the picture you rendered** and give `pdf_markup` `"px": [x0, y0, x1, y1]` (pixels of that picture, origin top left) with `"in": {"rect": <the rect you rendered>, "dpi": <its dpi>}`; with no `rect` the picture is the whole displayed page. Never convert pixels to points by hand.

## What real client sheets can look like (examples, not rules)
- A hand-marked **A3 scan** (about 200 dpi, no text layer) against an **A0 vector redraw** whose text is drawn as lines (so nothing can be searched), on one project; an **A1 PDF with a text layer** on another. Check what you have: `pdf_zones` says the size and whether there is a text layer.
- The page may be **rotated** (landscape shown from a portrait page): the tools handle it; positions are always as displayed.
- **The books do not line up page by page**: a cover sheet and a list of drawings may come first, the order may differ. Pair sheets by the **drawing number in the title block**, never by page number. A sheet in the list and not in the book (or the reverse) is a finding; so are revision, date and title block of each sheet.
- Marker colours on a hand-marked print: red pen = changes; blue pen = items ringed for the vendor or to check; yellow highlighter = what the client verified. If the sheet does not say what a colour means, ask the QC lead once and record it with `learn_record`. Handwriting that is not clear is a BLUE query, never a guess.
- Each area may come with a **drawings list and comments sheet** (things such as "sampling connections not in use", "instrument tags not available at site"). Read it (`file_read` on the Excel) before you check the area: a deliberate item is a query to confirm, not an error.
- **Office comment style** (the team's own comment sheets): keyed by line number or tag, short, one fact: `VALVE NOT FOUND`, `DRAIN NOT FOUND`, `LINE NOT ROUTED`, `INSTRUMENT NOT FOUND`.
- Typical items: instrument bubbles (tag over number), interlock diamonds, line numbers `size-service-area-seq-class` (for example `18"-SG-12-101-D1A`) and their size changes at reducers, vessel data tables, notes with referenced note numbers (a referenced note that does not exist is a RAW issue), off-sheet connectors, spec breaks (`D6A | A6A`), vendor scope boxes, "NOT IN USE" areas drawn as a cloud.

## 2. What to check (all of it, nothing skipped)
**A. Client markups.** Every markup on RAW must be in OUTPUT: red line numbers replacing XXX, cyan-highlighted items, struck-through text (is it removed?), "NOTE FOR CADDING" instructions (for example ball / butterfly valves replaced by the TCM standard symbols). List each markup as incorporated or not incorporated.

**B. Text and data.** Line numbers and sizes (1-1/2" vs 1/2" vs 1"); equipment, instrument and PSV tags (PSV-512F); PSV data boxes (set pressure, IN, OUT, orifice, case, ratings: 300 LB / 150 LB only where RAW shows them); PCV and control valve set pressures; equipment data tables, every row, label and value (psi vs psig); valve status labels NC / NO / FC / FO / LO / LC / ILO / ILC / CLOSE / V; pipe size text on lines and reducer sizes (3"x2", 6"x4", 14"x8"); notes, general notes, holds, equipment list, title block (wording, "AND" vs "&"), revision, date, prepared / checked / approved.

**C. Flow arrows, each one individually.** On every line, at every junction and tee on both sides where RAW shows them; at tank nozzles, equipment inlets and outlets, into and out of headers at each branch; on PSV outlets, ATM vents, flare risers, FREE DRAINING arrows, package inlet / outlet; the flow arrow under a self-actuated / regulator valve points the same way as in RAW; instrument signal arrows (PT to PLC to PI, TT to PLC to TI, LT to PLC to LI). Keep a count per zone (RAW arrows / OUTPUT arrows) so "checked OK" is a number.

**D. Drafting and symbols.** Valve symbols (ball, butterfly, gate, globe, check, control, XV, self-actuated) per TCM standard; equipment symbols as RAW (vaporizer / heater internals, outline thickness); line types (TCM interface dash-dot, signals dashed, process continuous) and line weights; line crossings (which line is broken, break symbols as RAW); VENDOR / TCM interface symbols (solid / hollow triangle, orientation, present in RAW, location); end caps, blinds, hoses, reducers, flanges, spectacle blinds, CL marks; text style and orientation (bold / underlined tags and titles, rotated text); the **VENDOR PACKAGE BOUNDARY** dash-dot line enclosing the complete package, routed as in RAW; border items (VENDOR / TCM split flags, grid zone references, position of data tables).

**E. Overlaps and clashes in OUTPUT.** Every text against linework and against other text (touching or crossed by a line, symbol, boundary line, leader or other text); symbol on symbol; lines too close to read. Mark in RED: "TEXT CLASH" or "OVERLAP" and the fix ("SHIFT TEXT CLEAR OF LINE").

**F. Spelling and grammar** of all text (notes, labels, tables, title block) and consistency (VAPOUR vs VAPOR, LIST vs LISTS, "SUBJECTED TO" vs "SUBJECT TO", placeholders such as "xx"). Error also in RAW: BLUE (client query). Only in OUTPUT: RED.

**G. Additions.** Anything in OUTPUT that is not in RAW (extra "XXXX" tags, headings, dates, names): a query.

**H. Raw issues.** Errors in RAW itself (a note referenced but missing, tag mismatch between table and drawing, duplicate tags): CLIENT QUERY (blue).

## 3. The markup PDF (`pdf_markup`)
- A **cloud around every error at its exact location**; a repeated error (Tank A and Tank B) gets **a cloud at each place** (`all: true`, or one item each). Types: `cloud`, `highlight` (yellow), `strikeout` (a line through the item), `legend`.
- The **comment is next to its cloud in a small box with a leader arrow** (the tool places it in free space, not on text, lines or other comments, and its arrow never crosses another comment, cloud or arrow). **No numbered list, no separate comment schedule.**
- **Comment style, the team's current preference: short, only what is to be done, with the value**: `UPDATE SCALE TO NTS`, `SET PRESSURE 150 PSIG`, `LINE SIZE 1-1/2" AS PER RAW`; about 50 characters (two lines). Not "RAW shows X, OUTPUT shows Y" (the QC lead's original prompt asked for that wording: use it only when the user asks for it, or when a query needs both values). To **strike out and replace**: a `strikeout` on the wrong text with the replacement in its comment.
- **RED** = correction required. **BLUE** = query / confirm / client query. **YELLOW HIGHLIGHT** (`type: highlight`) = every text or line in OUTPUT that was updated against RAW as per client markup (each new line number, changed value, changed line), placed on the item, text still readable.
- A **legend box** (`type: legend`) in an empty area: red / blue / yellow meaning, and a green "OK" line listing what was checked and found correct. A yellow legend line is printed black on a yellow band by the tool.
- **Placing by hand**: `at: [x, y]` is the **bottom left corner** of the comment box (or legend), in PDF points as displayed. A comment box is about 150 x K points wide (K = sheet size / A3: 1 on A3, 2 on A1, 2.8 on A0) and each line adds about 9 x K; the legend about 215 points high. When a zone is crowded and the tool reports "no place for the comment", give `at` for those comments (free paper beside the cloud, text short).
- **Characters**: capitals, Latin-1 only. Degree, squared, cubed and plus-minus are fine; anything else is reported as a warning and shows as `?`: spell it out (`M3`, `DEGREE`).
- The annotations are real (Polygon cloud, FreeText, Line, Highlight, StrikeOut): editable in Bluebeam and Acrobat.
- Several pages: one `pdf_markup` call with items for every page (`page`), one output file. Read the result's `warnings` (text not found, no place for a comment, characters that cannot be shown) and fix each one before you hand over.
- **Write once, check, then replace.** Look at the picture of your plan (or the first render) before writing the file; a markup file the tool wrote earlier is replaced without asking, but a file it did not write asks the user each time: write a new file name instead of overwriting the user's own.

## 4. Check before you hand over
For every page, `pdf_render` each **tile** of the **markup PDF** (same tile plan, same dpi) and look: every cloud sits on the right item, every highlight and strike-out is on its item, every comment is readable and overlaps nothing. Correct and repeat. Say how many zones you looked at.

## 5. Chat summary after the PDF (short)
Corrections (count and the main ones); overlaps; spelling / grammar; queries (client queries separate); flow arrows checked OK (count per zone); client markups incorporated / highlighted (and those not incorporated). Then **what was not checked or not sure** (a scan you could only read from pictures, a zone that was too dense, symbols you could not tell apart): never say a drawing is clean when a part was not looked at. Offer to save the findings as a report (`qc_report_write`). When the user corrects you or states a preference, record it with `learn_record`.

## Honest limits
- No tool compares drawing graphics automatically: the symbol, arrow, line-type and routing checks are your own reading of the zone pictures. Take your time, one zone at a time, and say how sure you are. A thing you cannot decide is a BLUE query, never a guess.
- Do not judge the design; compare OUTPUT with RAW (and with the TCM standard where the user gives it: ask for the symbol standard if it was not attached).
